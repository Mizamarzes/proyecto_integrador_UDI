# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project context

University "Proyecto Integrador" (UDI, Ingeniería de Sistemas, 4th semester, II-2026) spanning three courses: Ingeniería de Software I, Bases de Datos II and Programación II. The goal is a desktop app to register and process data from **Cuadernillo 2 (urban daily household expenses)** of the DANE *Encuesta Nacional de Presupuestos de los Hogares (ENPH)*.

Mandated constraints from the assignment: object-oriented design, **client–server architecture**, and persistence in a **relational database (Oracle)**. The UI is JavaFX.

Reference material lives in `docs/referencias/` (PDFs, in Spanish; `docs/README.md` indexes all docs):
- `Proyecto Integrador IV.pdf` — assignment statement, deliverables and deadlines.
- `Proyecto integrador IV semestre ... .pdf` — the team's design document: functional requirements (RF-01…, e.g. users/roles; the app currently uses only Admin/Encuestador/Crítico-digitador, household registration with a 14-day follow-up window, daily expense capture, special acquisition forms such as pago/regalo/trueque, case closure locking further inserts after day 14, visit tracking), ER/relational model and data dictionary. Consult it before implementing features or schema.
- `Cuadernillo 2 urbano.pdf` — the official DANE form whose fields the app must capture.

Use `pdftotext` to read these. Code, UI text and docs are written in Spanish; keep that convention.

## Commands

Requires JDK 21+ and Maven 3.6+.

```bash
mvn clean javafx:run     # run the app (main class com.udi.App)
mvn clean package        # compile and package
mvn compile              # compile only
```

There are no tests or test dependencies yet.

### Database (Oracle 10g XE in Docker)

The dev database runs in the local container `oracle-xe-10g` (host port 1522, SID `XE`, admin `system/oracle`). The app connects with the user in the local `db.properties` (the example and the commands below use `enph/enph`, but a developer's `db.properties` may point to another schema in the same container — check it before running scripts). To (re)create the schema:

```bash
# as system: DROP USER enph CASCADE; then
# CREATE USER enph IDENTIFIED BY enph DEFAULT TABLESPACE users QUOTA UNLIMITED ON users;
# GRANT CREATE SESSION, CREATE TABLE, CREATE SEQUENCE, CREATE PROCEDURE, CREATE TRIGGER TO enph;
docker exec -it oracle-xe-10g sqlplus system/oracle

docker cp docs/db oracle-xe-10g:/tmp/db   # whole folder: the script runs inserts/*.sql with @@
docker exec -it -e NLS_LANG=AMERICAN_AMERICA.AL32UTF8 oracle-xe-10g sqlplus enph/enph @/tmp/db/esquema_oracle10g.sql
```

- Locations come from `docs/db/inserts/` (`regiones.sql` 6 natural regions with ids 1–6, `departamentos.sql` 33 departments whose `id` is the DANE code, `municipios.sql` 1102 municipalities with ids 1–1102 that are not DANE codes), so `seq_region`/`seq_departamento`/`seq_municipio` start at 7/100/1103. `inserts/recargar_ubicaciones.sql` swaps the old 10-row test seed for these in an existing database.
- The `ZHS16GBK` charset has no `ñ`/`Ñ` and no uppercase accented letters: `ñ` is stored as `?` and `Á` turns into `á` (e.g. `Nariño`, `Útica`).

- `NLS_LANG` is required: the database charset is `ZHS16GBK`, and accented text is corrupted without it.
- The seed data uses hard-coded FK ids (1, 2, 3…), so the script only works on an empty schema with sequences starting at 1. There is a commented cleanup block at the top of the script.
- Seed users all have password `123456` (stored as SHA-256 hex). `admin@enph.udi.edu.co` is ADMIN, `cperez@…` is CRITICO_DIGITADOR, `lmartinez@…` and others are ENCUESTADOR, and `rcastillo@…` is inactive.
- `grupo_alimento` and `lugar_compra` use the cuadernillo's official codes as their `id` (groups 1–25; places 1, 4, 6, 7, 10, 13, 14, 16–25), so their sequences start at 26. `BaseDAO.asignarId` keeps an id that is already set and only takes `NEXTVAL` when it is null.

## Architecture

Java 21, JavaFX 21, `javafx-maven-plugin` 0.0.8, Oracle 10g via JDBC (`ojdbc6` 11.2.0.4 — newer drivers cannot connect to a 10g server). MVC with the model split into layers; the full tree, layer rules and business rules are in `docs/arquitectura/arquitectura.md`. The backend (model, DAO, service) exists. Frontend done: login, the main shell (`ui/shared/layout/navbar.fxml`: sidebar + header with Reportes, Encuestas, Viviendas y hogares, Verificación, Usuarios and Roles y permisos; after login it opens the first visible module in that order), Encuestas (role-aware list, "nueva encuesta" modal that only picks a household, and `encuesta_detalle` with six tabs: Visitas, Cap. A, Cap. C, Línea de 14 días with D/D1, Cierre with D2 and the closing checklist, and Correcciones, which lists every review from `auditoria_encuesta` via `EncuestaService.revisiones`; only the latest rejection of a RECHAZADA survey is marked pending), Viviendas y hogares (list, detail, vivienda and hogar modals), Reportes (`modulos/reportes/reporte`: a dashboard filtered by region/department/municipality and a date range on the survey start date (`fecha_desde`), applied together with a "Filtrar" button ("Limpiar" clears and reloads), with KPIs, survey status, spending by type, acquisition form and purchase place, food groups from Cap. C, a per-encuestador table paginated in memory (10 per page, the Total row is repeated on every page and the export includes every row), and "Exportar a Excel": an .xlsx with one sheet per section, written by `util/LibroExcel` (a minimal Office Open XML writer over `java.util.zip`, no external library, so nothing new in `module-info`); queries live in `dao/reportes/ReporteDAO`, which does not extend `BaseDAO` and uses its public `asignarParametros`; an ENCUESTADOR with the `reportes` module only sees their own surveys; `gasto_diario` has no food group, so the food-group chart counts households from `caracteristica_gasto`), Verificación (`modulos/verificacion/verificacion`, RF-10, for the CRITICO_DIGITADOR: a tray of PENDIENTE_APROBACION/RECHAZADA/APROBADA surveys with two cards (Pendientes de aprobación, Aprobadas), and a side panel with the cross-validation computed by `VerificacionService` (9 rules, each CORRECTA/AVISO/ERROR; errors block approval, warnings don't), the actions for its state and the case history from `auditoria_encuesta`. Survey states (`EstadoEncuesta`) are EN_CURSO, PENDIENTE_APROBACION, APROBADA and RECHAZADA: closing a case sets PENDIENTE_APROBACION; "Rechazar" requires an observation and moves it to RECHAZADA (editable again; the survey detail shows the observation in a banner, and closing it again sends it back as PENDIENTE_APROBACION); "Aprobar y exportar a Excel" asks for the file first, sets APROBADA (no further changes) and writes one sheet per chapter (A/D2, B, C, D, D1) with `util/LibroExcel`; an ADMIN reopening a pending or approved case sets EN_CURSO. `auditoria_encuesta.accion` (`AccionAuditoria`) only allows APROBADA and RECHAZADA, so closing, reopening and exporting are not recorded in the history. Schemas with the old five states are converted by `docs/db/migraciones/migracion_estados_encuesta.sql`), Usuarios and Roles y permisos (`modulos/roles/rol`: a roles × modules checkbox matrix over `rol_modulo`, saved in one transaction by `RolService.guardarPermisos`, plus the `rol_form` modal; the ADMIN row is locked). Roles can't be renamed (the code matches ADMIN and ENCUESTADOR by name); they are only created or deleted. ADMIN and ENCUESTADOR are system roles (`Rol.esDelSistema()`) that `RolService` refuses to delete; ENCUESTADOR's permissions are still editable. Tabs and modals live in each module's `partials/`; tab controllers implement `SeccionEncuesta`, and modals open through `util/Modal`. `ui/shared/layout/pendiente.fxml` is a reusable "en construcción" placeholder. The closing checklist is only enforced in the UI; `EncuestaService.cerrar` only checks that the survey is editable.

- Layers: `controller` → `service` (business rules, throws `ReglaNegocioException`) → `dao` (SQL only, one per table, extends `BaseDAO`, which stays in `com.udi.dao`) → `model` (entities extend `Entidad`/`EntidadAuditable`; enums in `model/enums` map to `VARCHAR2 + CHECK`). Controllers must never call DAOs.
- Database access: `config/ConexionBD` keeps a single shared connection (opening one per operation exhausts Oracle XE processes, ORA-12519). Services wrap reads in `ConexionBD.consultar(c -> ...)` and writes in `ConexionBD.enTransaccion(c -> ...)`; DAO methods take the `Connection` as first parameter. Connection settings live in `src/main/resources/com/udi/config/db.properties`, which is git-ignored (copy it from `db.properties.example` next to it), and can be overridden with `-Ddb.url`, `-Ddb.usuario`, `-Ddb.contrasena`.
- Business logic uses no triggers: ids come from `seq_<tabla>.NEXTVAL` (assigned in each DAO's `insertar`), `updated_at = SYSTIMESTAMP` is set in each DAO's `actualizar`, and all cross-table rules (closed survey RF-06, personal expenses only days 1–7, day date = `fecha_desde + numero_dia - 1`, chapter C complete before daily records) are enforced in the services. `created_by` comes from `util/Sesion`. Shared survey rules live in `service/encuestas/ReglasEncuesta`. Service writes check the same module permission as the views with `Sesion.exigirModulo(RutasModulo.X)` (admin always passes); catalogs and locations still require `Sesion.exigirAdmin()`, and role-based business rules stay (only an ENCUESTADOR creates a survey, only ADMIN reopens one or assigns/edits ADMIN users). The only triggers are the audit ones from `docs/db/migraciones/migracion_auditoria.sql` (also run at the end of `esquema_oracle10g.sql`, after the seed): table `auditoria` + `seq_auditoria`, procedure `incluir_auditoria`, function `fn_usuario_sesion` and one `trg_cud_<tabla>` per table (AFTER INSERT OR UPDATE OR DELETE, FOR EACH ROW, following the professor's style in `docs/referencias/`). They only read `:NEW`/`:OLD` (no queries, to avoid ORA-04091 on cascades) and never log the password. `auditoria.usuario_id` is the session's `CLIENT_IDENTIFIER` (set it with `DBMS_SESSION.SET_IDENTIFIER`) or, on inserts, the row's `created_by`; the app doesn't set the identifier yet. Accented text in audit descriptions must avoid `ñ` (ZHS16GBK).
- Enum columns store the constant name (e.g. `FormaAdquisicion.COMPRA`), not the numeric code; booleans are `CHAR(1)` `'S'`/`'N'`. `BaseDAO` does these conversions in both directions.
- Schema source of truth: `docs/db/modelo_relacional.dbml` (documented in `modelo_relacional.md`); DDL and seed data in `docs/db/esquema_oracle10g.sql`; diagrams in `docs/db/diagramas/`. When the schema changes, update them in that order and keep the DAO column lists in sync. The UI design prompt is `docs/diseno/prompt_diseno_ui.md`.
- Java Platform Module System: `src/main/java/module-info.java` declares module `com.udi` and `requires java.sql`, `java.prefs` (login "Recordarme") and `ojdbc6` (automatic module). Any new package that FXML controllers live in (each `com.udi.controller.<modulo>`) must be `opens ... to javafx.fxml` (and `opens com.udi.model to javafx.base` if `PropertyValueFactory` is used), and new dependencies must be added as `requires`, or runtime/compile will fail. Don't `opens` a package before it exists — compilation fails.
- Packages by module: `controller`, `service` and `dao` each have one subpackage per module — `auth`, `shared` (only `NavbarController`), `usuarios`, `roles`, `viviendas`, `encuestas`, `reportes`, `verificacion`, and `catalogos` (services/DAOs for regions, departments, municipalities, food groups and purchase places). E.g. `com.udi.controller.encuestas.EncuestaController`, `com.udi.service.viviendas.HogarService`, `com.udi.dao.usuarios.EncuestadorDAO`. Members used from another module must be `public` (e.g. `ReglasEncuesta`, `EncuestaController.insigniaEstado`, `ViviendaController.textoClase`). Every controller subpackage needs `opens com.udi.controller.<modulo> to javafx.fxml;` in `module-info.java`, and FXML `fx:controller` uses the full package.
- Views: FXML/CSS resources are organized by module under `src/main/resources/com/udi/ui/`: `ui/modulos/<modulo>/*.fxml` (auth, encuestas, usuarios…; `partials/`/`components/` subfolders if a module needs modals or fragments) and `ui/shared/` (`estilos.css`, `layout/navbar.fxml`, `layout/pendiente.fxml`). Styles are split the same way: `ui/shared/estilos.css` holds the color tokens and components used by several modules (buttons, fields, tables, cards, status badges, banners, modals, `SelectBuscable`, `Paginador`) and is attached to the scene and to every modal; module-only styles go in `ui/modulos/<modulo>/estilos.css` and the shell's in `ui/shared/layout/estilos.css`. `App.cargar` adds the folder's `estilos.css` (if present) to each loaded view's root, so FXML doesn't declare stylesheets. A module sheet only applies inside that module's views, so a class used by a second module moves to the shared sheet; popups (`SelectBuscable`) copy only the scene stylesheets, so their styles stay shared. A view is named by its path inside `ui` without extension, e.g. `"modulos/encuestas/encuesta"`.
- Navigation: `App` holds a single static `Scene` (with `ui/shared/estilos.css` attached) and starts on `modulos/auth/login`; views are swapped by calling `App.setRoot("<vista>")`, which loads `src/main/resources/com/udi/ui/<vista>.fxml`. Inside the shell, `NavbarController.abrir("<vista>", migas...)` loads a module view into the content area and returns its controller (to pass data, e.g. `editar(id)`). Access control lives in `com.udi.middleware`, modeled on an Express router (`isAuth, ModulePermissionMiddleware`): `Rutas` maps view-path prefixes to a chain of `Middleware`s (`modulos/auth/` public; `modulos/usuarios/`, `roles/`, `viviendas/`, `encuestas/`, `reportes/`, `verificacion/` → `AutenticacionMiddleware` + `PermisoModuloMiddleware`; anything else → authentication only). `PermisoModuloMiddleware` lets ADMIN through and otherwise resolves the view's module slug with `RutasModulo.slugsDe(vista)` and checks it against the session's `rol_modulo` rows. There are 6 modules, one per top-level folder: `usuarios`, `roles`, `viviendas` (viviendas y hogares), `encuestas` (the survey and all its tabs: visitas, Cap. A, Cap. C, gastos D/D1, cierre), `reportes` and `verificacion`. Schemas created with the old 10-module seed are converted by `docs/db/migraciones/migracion_unificar_modulos.sql`; schemas created before Verificación (no `auditoria_encuesta`, `encuesta.estado` VARCHAR2(10)) by `docs/db/migraciones/migracion_verificacion.sql`. `App.cargar` calls `Rutas.exigir(vista)` before loading any screen, tab, form or modal, throwing `AccesoDenegadoException`. Don't add role checks in controllers: add a route in `RutasModulo`/`Rutas`, hide buttons with `Rutas.permitir(nodo, vista)` (sidebar, new/edit buttons, links across modules); inside a survey, editing only depends on `EncuestaDetalleController.esEditable()`. Permissions are loaded at login, so edits apply on the next login (except the session's own role, which `RolService` reloads). A global uncaught-exception handler on the FX thread (set in `App.start`) shows these errors as alerts. Services still check on their own (`Sesion.exigirModulo`, e.g. all `UsuarioService` user reads and writes need `usuarios`); other screens get a user's name via `UsuarioService.nombreUsuario`. Controllers live in `com.udi.controller.<modulo>`, call services through `util/Tareas.ejecutar` (background, one at a time, errors shown with `util/Alertas`) and use lambda cell factories in tables (no `PropertyValueFactory`, so `model` needs no `opens`).
- Reusable FXML controls live in `com.udi.componentes` (opened to `javafx.fxml`). `SelectBuscable<T>` is the searchable, paginated select (search box + "Ver más" at the end of the list), fed by a `Fuente` that calls a service returning `model/Pagina<T>`; DAOs paginate with `BaseDAO.consultarPagina` (ROWNUM, Oracle 10g has no OFFSET) and search accent-insensitively with `patron`/`sinTildes`. Region/department/municipality selects are chained by `controller/viviendas/SelectoresUbicacion` (form and listing filters). Use it instead of `ComboBox` for long catalogs. `Paginador<T>` is the in-memory table pager (CSS `.paginacion`, 10 rows per page): put it under the `TableView` in FXML and call `paginador.vincular(tabla, filtradas, "singular", "plural")`; it sets the table items to the current page and sorts the whole list via a `SortedList` bound to the table comparator. Optional `setFilaFinal(supplier)` repeats a row at the end of every page (the Reportes Total row) and `ajustarAlto(altoFila)` fixes the table height to one full page. The Encuestas, Viviendas, Usuarios and Reportes (per-encuestador) tables use it.
- An ENCUESTADOR only sees and modifies the viviendas and hogares they created (`created_by`), enforced in `HogarService` (listings filter in the DAO; the viviendas module opens a detail through `buscarViviendaVisible`; writes check ownership). `buscarVivienda`/`buscarHogar` stay unfiltered because the survey detail uses them and its household may have been created by another user.
- `vivienda` has no `total_hogares` column: A.12 is the number of registered households, computed by `ViviendaDAO` (which also joins municipality/department/region names into `Vivienda`). Older schemas are converted by `docs/db/migraciones/migracion_quitar_total_hogares.sql`.
- Each FXML binds its controller via `fx:controller` and handler methods via `onAction="#method"`; handlers are `@FXML private` methods in the controller.
